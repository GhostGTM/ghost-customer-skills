---
name: workflow-build
description: Build a new Ghost workflow from a goal: plan the stages, create the cards with bindings and success criteria, set Slack or email delivery, review and cadence, validate, run a sample, publish, and arm the schedule. Use for "make this recurring", "build a workflow that..."; use workflow-run to operate one that exists.
argument-hint: "[goal in one sentence] [cadence, destination and reviewer if known]"
---

Read `${CLAUDE_PLUGIN_ROOT}/references/working-with-ghost.md`. Workflows exist only in the Ghost API: this needs `GHOST_API_KEY` with both `workflows:read` and `workflows:run`, and the key owner becomes the workflow's author. Without a key, produce the plan and the card list as a handoff.

Every mutation is a `POST /operations` call with the user's words as `reason` and a fresh `Idempotency-Key`; poll the receipt and read `result` before continuing. Reads go through `POST /query`. Builder calls use `workflows.builder.<tool>` with `{ workflowId, arguments: { ...toolFields } }` as the outer arguments, including `{}` for no-input tools. The five confirmation gates below approve the exact plan and payloads presented at each gate. Reads need no confirmation, and one approval covers the presented batch.

Validation or judge feedback does not authorize a changed mutation payload. Show revisions and obtain approval before adding cards or human gates, changing recipients, channels, reviewers, destinations, cohort, cost, or cadence, or otherwise changing the approved plan. Repairs that only implement the exact approved payload can proceed under the existing approval; reconcile receipts before retrying any uncertain write.

**1. Goal and plan (gate one).** Restate the goal as the outcome the user will read, the cadence, the destination (Slack channel names, email recipients), and who reviews each report and where (a Slack DM to each reviewer, or one card in a review channel). Confirm, then `workflows.create` with `name` and `template: "blank"`, `workflows.builder.set_workflow_goal`, and `workflows.builder.plan_workflow_stages` with the goal. Use `describe_systems` and `search_workflow_fields` to learn which system holds each field before designing cards. Match the execution contract to that system: `load_accounts` reads HubSpot and requires its connection; setting `platform: "ghost-graph"` alone does not change it. To read existing Ghost accounts, use an explicit binding with `source: "ghost-graph"`, `entity: "accounts"`, and the intended fields/predicates.

**2. The cards (gate two).** Present the full card list once, in execution order, and one yes applies all of them. Each card: `id` (kebab-case), `kind`, `icon` (from the catalog enum), `title`, `col`, `row`, `operation`, a pinned `binding`, or an `intent` with `tools` for an open card, `params`, `success_criteria`, and `connect_from`. Kinds: `source`, `rule`, `enrich`, `gather`, `ai_judgment`, `ai_generation`, `context_doc`, `human_gate`, `action`, `notify`. Operations include `load_accounts`, `load_calls`, `filter_untouched`, `filter_by_activity`, `merge_dedupe`, `find_people`, `resolve_account_cohort`, `load_account_facts`, `load_account_activity`, `classify_icp`, `apply_ai_fields`, `select_contacts`, `research_accounts`, `ground_context`, `generate_sequence`, `compose_report`, `upsert_graph_entities`, `write_hubspot_records`. The catalog's `validate_workflow` output and the operation list in the builder tool are authoritative.

Ordering rules the server and the run judge enforce: select before qualify, qualify before anything that spends, ground before generate, rank before cap, and a `human_gate` immediately before every `action` or `notify` card. Send `connect_from` as an array of `{ "from": "<existing step id>", "style": "default" }` objects, not strings. Execution order comes from `connect_from`, not from the order cards were created. A success criterion states only what the card guarantees; an overstated one halts correct runs.

Apply with `workflows.builder.upsert_workflow_step` per card and `bind_card_fields` for pinned fields. Run `validate_workflow` and fix every error before moving on; show warnings.

**3. Delivery, review and cadence (gate three).** Read `workflows.slack_channels` (pass the channel name as `query`) and `workflows.delivery`. Present two payloads for one yes:

- `workflows.set_delivery`: `slack: { enabled, channels: [{ "name": "renewals-digest" }] }` by name, or `{ "id": ... }` only when the user gives one (the way to name a private channel Ghost is not in yet); `email: { enabled, addresses }`; and `review: { enabled, mode, channel?, reviewerEmails? }`. Mode `dm` sends each reviewer the review card as a Slack DM; mode `channel` posts one card in `channel`, named the same way. Name reviewers by work email in `reviewerEmails`, at most 10, each the email of a member of this workspace, and none means the author reviews. Ask the user for any email you do not have and never guess one from a name. When the only reviewer is the key owner, `reviewerUserIds` with the identity's `userId` also works; send one list, never both. A reviewer outside this workspace's Slack gets no DM card: use channel mode in a channel they share, which a Slack Connect guest can decide.
- `workflows.set_cadence`: `days` (`mon` to `sun`), `time` as 24-hour `HH:MM`, and an IANA `timezone` such as `America/Los_Angeles`. It does not turn the schedule on. Skip it for a manual workflow.

A refused channel name or reviewer email returns the reason; show it and ask, do not guess an id or an address. After the receipt, read `readiness` and `nextStep` for every channel, the review channel included:

- `ready` or `joined`: Ghost can post. Say so.
- `needs_invite`: give the user `nextStep` word for word (in that channel, type `/invite @Ghost` and pick Ghost; someone already in the channel does this). Wait until they say it is done, then read `workflows.delivery` and report the new status. Repeat until it reads `ready`. Do not resend the write.
- `not_found`: the channel is archived. Ask for another; a new channel is a changed payload.
- `unknown`: Ghost could not check. It blocks nothing; say so and check again later.

While a Slack delivery channel reads `needs_invite` or `not_found`, Ghost refuses to accept a report or turn the schedule on. While the review channel does, no review card is posted.

**4. Sample run (gate four).** Confirm, then `workflows.builder.start_workflow_run` with `fidelity: "sample"` and `user_said` copied verbatim from the `reason` you send; the server rejects consent it cannot find in `reason`. Sample runs never execute outward cards. Poll `workflows.state` until the run settles; check `status`, `haltedReason`, and each step's `verdict` and `verdictReasoning`. Read `workflows.artifact` with `workflowId` and `runId`. For a table, take the returned `outputId` into `workflows.rows` and verify the actual rows; for a document, read the artifact body. A missing artifact or output is a retrieval gap, not permission to invent rows or start another run. `fidelity: "sample"` is authoritative even when `kind: "full"`: orchestrated samples use that combination. `get_test_run_digest` supports only legacy runs whose `kind` is `test`, so do not call it for an orchestrated sample. Show the user real output and the judge's notes, and repair cards before publishing.

**5. Publish and arm (gate five).** Confirm, then `publish_workflow` with `confirm: true` (refused until validation is ready), then, for a recurring cadence, read `workflows.schedule` and send `workflows.set_schedule` with `enabled: true`. It is refused without a cadence, with a connector not ready, or with a Slack delivery channel not ready; report the server's sentence, and for a channel give its `/invite @Ghost` step and check again as in gate three. A manual workflow is published for on-demand runs and has no schedule to arm. If the user would rather decide after seeing a real report, leave the schedule off: the accepted Slack review card offers the reviewer a Turn on button with a recommended cadence. Report the schedule summary the server returns; `definition.schedule.enabled` alone does not arm anything. Scheduled runs run as whoever turned the schedule on.

Report the workflow id, version, schedule, delivery and its readiness, who reviews and where, and what a full run will do that the sample did not. Do not start a full run or send a deliverable unless asked; those are workflow-run actions with their own consent. With review on, a full run's report waits in Slack until a reviewer accepts it.
