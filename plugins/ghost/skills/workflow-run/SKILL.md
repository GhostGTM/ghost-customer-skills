---
name: workflow-run
description: Operate an existing Ghost workflow: see its state, runs, rows, and artifacts; start a run; decide a report held for review or approve a gate; set Slack or email delivery, review, and cadence; pause or arm the schedule; archive. Use for "did my workflow run", "send it to #channel", "turn it on every Monday", "turn it off"; use workflow-build to create one.
argument-hint: "[workflow name] [what to check or do]"
---

Read `${CLAUDE_PLUGIN_ROOT}/references/working-with-ghost.md`. Workflows exist only in the Ghost API: reads need `GHOST_API_KEY` with `workflows:read`, mutations need `workflows:run`, so a read-then-write task needs both grants. Publishing requires the workflow author. Full runs, gates, delivery, review settings, cadence, the schedule (the builder's `set_workflow_live` included), and archiving allow the author or a workspace admin; an editor grant does not. Builder calls use `workflows.builder.<tool>` with `{ workflowId, arguments: { ...toolFields } }` as the outer arguments. Without a key, say so and stop.

Find the workflow with `workflows.list` (paged with `cursor`) and `workflows.get`; show candidates if the name is ambiguous. `access.canEdit` indicates edit access, not permission to publish, arm, run, or change delivery; check the operation-specific authorization too. When the key owner is neither the author nor a workspace admin, say before any such write that it will be refused and offer to ask one of them; never route around it with builder tools, another key, or a duplicate.

**Reads, no confirmation.** `workflows.state` for the latest run or a given `runId`: status, cursor step, halted reason, per-step status, deliveries, model cost. `workflows.runs` for history. `workflows.rows` with the output id, `page`, and `pageSize` for the table a step produced; the newest step with rows is found by following edges, not by list position. `workflows.artifact` with `workflowId` and `runId` for the stored result; its `outputId` identifies the table for `workflows.rows`. `workflows.schedule` for cadence and health (`on`, `off`, `paused`, `degraded`) and `turnedOnBy`. `workflows.delivery` for Slack channels, email recipients, review mode, reviewers (`review.reviewers` gives each one's name and email) and review channel, with `readiness` and `nextStep` for each channel. `workflows.slack_channels` (with `query`) for the channels Ghost can post in. `workflows.reviews` for reports waiting on the key owner, with their `revision`. `workflows.builder.read_workflow_run_log` for a failing step's notes, and the step `verdict` / `verdictReasoning` from `workflows.state` for the judge's result. `get_test_run_digest` only supports legacy `kind: "test"` runs. An orchestrated sample has `kind: "full"` and `fidelity: "sample"`; use its state and artifact and do not mistake the kind for authorization to deliver.

Explain a halt from the log and the step's success criterion before proposing a change. A run waiting at a `human_gate` needs a decision, not a restart. A finished full run whose report is held for review needs a reviewer's accept, not a rerun.

**Channel readiness.** Every channel answer carries `status` and `nextStep`. `ready` and `joined` can post. `needs_invite`: give the user `nextStep` word for word (in that channel, type `/invite @Ghost` and pick Ghost; someone already in the channel does this), wait until they say it is done, then read `workflows.delivery` again and report the new status; repeat until `ready`, and never resend a write to check. `not_found`: archived; ask for another channel. `unknown`: Ghost could not check; it blocks nothing. While a Slack delivery channel is `needs_invite` or `not_found`, Ghost refuses to accept a held report or turn the schedule on.

**Mutations, each confirmed.** State the workflow, the action, and what it will touch, then wait for a yes. Submit with `POST /operations`, the user's words as `reason`, and a fresh `Idempotency-Key`; poll the receipt.

- Start a run: `workflows.builder.start_workflow_run` or `workflows.run`, with `fidelity` and `user_said` copied verbatim from the actual approval in `reason`. Bare run or test approval means `sample`. Full requires explicit real/full/live run or delivery approval; never promote sample consent to full. Both routes run the same consent and readiness checks and default to sample. A full run runs as the key owner and executes outward cards behind approved gates; say so. With review on, its report waits until a reviewer accepts it: say who reviews and where (a Slack DM to each reviewer, or one card in the review channel), and that nothing goes out before then. Do not decide the review for them.
- Decide a held report: `workflows.review_output` with `reviewId` and `expectedRevision` from `workflows.reviews`, and `decision` `{ "kind": "accept" }`, `{ "kind": "reject", "reasonCode" }`, or `{ "kind": "revise", "instruction" }`. Only a listed reviewer or the author may decide. Read `result.ok`: `ok: false` wrote nothing; with `reason: "destination_not_ready"` give its `message` (the invite step), follow Channel readiness, and offer the accept again as a new confirmed action with a fresh `Idempotency-Key`.
- Approve or reject a gate: `workflows.review_gate` with `runId`, `decision`, and a `note`. Show what the gate protects (the rows and the outward card) before asking.
- Resume a paused run: `workflows.resume`. Continue a long-run checkpoint: `workflows.continue`.
- Set delivery and review: `workflows.set_delivery` with any of `slack: { enabled, channels }`, `email: { enabled, addresses }`, and `review: { enabled, mode, channel?, reviewerEmails? }`; a part left out keeps its value. Name channels as `{ "name": "renewals-digest" }`, or `{ "id": ... }` only when the user gives one. Mode `dm` DMs each reviewer the card; mode `channel` posts one card in `channel`, which a Slack Connect guest in a shared channel can decide. Name reviewers by work email in `reviewerEmails`, at most 10, each the email of a member of this workspace; ask the user for any you do not have and never guess one from a name. None means the author reviews. When the only reviewer is the key owner, `reviewerUserIds` with the identity's `userId` also works; send one list, never both. `workflows.set_review` changes review alone: `reviewEnabled` and one of the two lists are required, and `reviewMode` and `reviewChannel` keep their values when left out. A refused channel name or email returns its reason, such as "x@example.com is not a member of this workspace."; show it and ask. After the receipt, apply Channel readiness to every channel, the review channel included.
- Set the cadence: `workflows.set_cadence` with `days` (`mon` to `sun`), `time` as 24-hour `HH:MM`, and an IANA `timezone`. Report the returned `sentence` and `on`. It never turns the schedule on; a schedule already on moves to the new cadence at once.
- Pause or arm the schedule: read `workflows.schedule` first; the reviewer may already have turned it on from the Turn on button on an accepted Slack review card. Then `workflows.set_schedule` with `enabled`. Arming needs a cadence (set it first with `workflows.set_cadence`), ready connectors, and ready Slack delivery channels; report the server's sentence, and for a channel give its invite step. Scheduled runs run as whoever turned the schedule on; say whose that will be.
- Send a deliverable: `workflows.builder.draft_deliverable_send` drafts first; a second call with `send_now: true` and `user_said` sends. Two separate confirmations.
- Archive: `workflows.archive` turns the schedule off and hides the workflow; not reversible from here.

Report the receipt's result verbatim. On `outcome_unknown`, read the state of the exact target: `workflows.schedule` for schedule and cadence changes, `workflows.delivery` for delivery and review changes, `workflows.state` for runs, `workflows.reviews` for review decisions, and the deliverable's delivery history for sends. If the requested effect already happened, report it and do not resubmit. Do not edit cards from this playbook; route definition changes to workflow-build so validation runs.
