Read `${CLAUDE_PLUGIN_ROOT}/references/working-with-ghost.md` and `${CLAUDE_PLUGIN_ROOT}/references/api-requests.md`. This path requires a matching API identity with `graph:read`, `graph:write`, and `research:run`; live HubSpot reads also require `crm:read`. The caller must be an owner, admin, or analyst. Check the live catalog for availability and the exact schemas of `graph.agent_preview` and `graph.agent_run`.

Claude Code creates the plan. Gemini executes it inside Ghost: it chooses among the approved reads, evaluates their evidence, and directly applies permitted field changes and selected context matches. Do not insert a second Gemini confirmation or proposal stage. A user can instead ask for a draft plan only; that does not authorize execution.

1. Resolve explicit account IDs and read their account detail, full firmographics, contacts, evidence, and selected context definitions. Account/contact records expose CRM IDs and related-data links; page relevant collections. Keep canonical person IDs, `account_people.id`, Ghost account IDs, and CRM IDs distinct. For this executor, `personId` means `account_people.id`.
2. Select the smallest useful field allowlist and/or exact ICP, persona, product, use-case, or competitor IDs. Accounts are capped at 20; all IDs must belong to this workspace. Account fields fill empty values only. Person fields may be corrected. Context matches add associations; they preserve existing matches. Removing a match, overwriting firmographics, creating contacts, and editing arbitrary custom fields require another supported path and its own scoped authorization.
3. If live sources are needed, discover their field keys through `graph.browse_field_catalog` or `graph.search_connected_api_fields`, then build named `connectedReads`. Each names an account, source, entity, exact selected fields and filters, and row limit. Gemini can choose a named read; it cannot change its query. Use known CRM object IDs or other verified identifiers in predicates. Inspect connector filtering/coverage notes: a named account on the plan does not itself prove a connector filter isolated that account. Never treat other accounts in returned data as authority to edit them.
4. Call `graph.agent_preview` through `POST /query`. Show the complete plan: objective, exact accounts, permitted fields/targets, connected queries, change limit, model-call limit, and model credit ceiling. The preview calls no model and changes nothing, but the normal successful API-call fee applies. Submission also has an API fee; provider usage is additional. Reads made while planning have their own normal API fees. Use the returned ceiling, never a guessed dollar price.
5. Obtain or use the user's existing explicit approval for that exact scope and cap. Submit once through `POST /operations` with `mode: "apply"`, sufficient `creditCap`, a fresh idempotency UUID, and the user's approving words copied verbatim into `user_said` and `reason`. The words must approve applying/updating the scoped edits; approval to preview, propose, or run a sample is insufficient. Changed accounts, queries, fields, targets, or budget need renewed scope approval. Do not reuse unrelated workflow consent.
6. Poll the receipt. Gemini may perform several metered model calls per account, reading approved sources before applying changes. It will not ask the user again about each discovered value. On completion report verified changes, skipped items and reasons, coverage, model calls, and recorded model credits separately from API fees. Read back affected records. A partial result or `needs_review` can include applied edits; it is not proof that nothing changed.

The executor uses at most 100 contacts and 12 recent source excerpts per account plus the selected context and approved connected reads. It reports limits and requires cited evidence. Model judgments can still be wrong; do not describe confidence as certainty or claim the entire workspace was reconciled from a bounded packet.

If access is denied, stop. If a provider call, write, or billing record is uncertain, preserve the receipt and inspect its per-account checkpoints, usage, and actual graph state. Never automatically replay the whole run or increase the cap. Already-applied changes remain applied when a later account fails. `creditCap` bounds model work for this run; it does not include API fees or subsequent runs. User-requested model work is billed under `graph.agent_run` / `agent_run` / `api`, separately from core ingestion. This executor does not send messages, write the CRM, enable schedules, delete records, or remove existing context matches.
